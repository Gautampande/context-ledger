# v1.5.0 handoff value evaluation

## Goal

Test a narrow, falsifiable claim: does a retrieval-selected Context Ledger handoff help a receiving chat answer a declared continuation task better than a recent raw-conversation tail under the same declared maximum historical-content byte budget?

This is **not** a claim that one model, prompt, conversation, or score proves general AI quality. It is a reproducible comparison for a declared source, task, destination configuration, and scoring process.

## What the command creates

`evaluate-handoff` is local-only. It validates the archive and local index, then creates a new private directory containing:

- `retrieval-handoff.md`: the normal reviewed Context Ledger handoff selected by the query.
- `raw-tail-baseline.md`: the most recent source messages under the same maximum historical message-content byte budget. If the next older message would exceed the remaining budget, its retained tail is explicitly labeled as an excerpt. The manifest records actual used bytes; it may leave a few bytes unused rather than split a Unicode code point.
- `evaluator-instructions.md`: the fixed task, procedure, and 0–2 scoring rubric.
- `evaluation-manifest.json`: archive/transcript binding, selected event IDs, byte budgets, SHA-256 values, and stated limitations.

It makes no AI request, sends no network request, estimates no model tokens, and scores no answers. The comparison uses the same maximum UTF-8 historical-message-content byte budget for both sides; fixed headings, safety instructions, and explicit truncation labels are excluded. The manifest records actual totals and preserves Unicode code-point boundaries rather than pretending a byte-exact match where one is impossible.

## Reproducible synthetic walkthrough

The repository fixture is synthetic and safe to disclose. It puts the relevant security decisions earlier in a conversation while the raw tail contains later unrelated UI discussion.

```sh
STUDY_DIR="work/v1.5-study-$(date +%Y%m%d%H%M%S)"

node src/cli.js import-json \
  --input fixtures/evaluation/handoff-study.json \
  --out "$STUDY_DIR"

ARCHIVE_PATH=$(find "$STUDY_DIR" -type f -name 'archive.aicx.json' -print -quit)

node src/cli.js evaluate-handoff \
  --archive "$ARCHIVE_PATH" \
  --query 'PKCE authorization decision' \
  --task 'State the authorization decision, identify the responsible teams, and cite supporting event IDs. Mark anything not in the supplied context as unknown.' \
  --out "$STUDY_DIR/evaluation-kit"

open "$STUDY_DIR/evaluation-kit/evaluator-instructions.md"
```

Read the generated instructions before using either context in an external chat. Use two separate fresh chats, the same product/model/settings/output limit where possible, and exactly the generated task. Do not add explanation or source material to one side but not the other.

## Predeclared release scenarios

For the `v1.5.0` synthetic evaluation, run all three scenarios below against the same imported synthetic archive. Each command writes a distinct kit. Do not change the query or task after looking at either context or answer.

```sh
node src/cli.js evaluate-handoff \
  --archive "$ARCHIVE_PATH" \
  --query 'PKCE authorization decision' \
  --task 'State the authorization decision, identify the responsible teams, and cite supporting event IDs. Mark anything not in the supplied context as unknown.' \
  --out "$STUDY_DIR/evaluation-pkce"

node src/cli.js evaluate-handoff \
  --archive "$ARCHIVE_PATH" \
  --query 'diagnostic logs redaction' \
  --task 'State which values must be redacted from diagnostic logs, state what may be logged, and cite supporting event IDs. Mark anything not in the supplied context as unknown.' \
  --out "$STUDY_DIR/evaluation-logging"

node src/cli.js evaluate-handoff \
  --archive "$ARCHIVE_PATH" \
  --query 'production database' \
  --task 'State whether this conversation selects a production database. Cite supporting event IDs and do not infer a database choice that is not recorded.' \
  --out "$STUDY_DIR/evaluation-unknown"
```

The first two scenarios test retrieval of earlier decisions and responsibilities. The third is deliberately an uncertainty test: a correct answer must not invent a production database. Record an outcome for all scenarios, even if neither packet helps or a destination chat fails.

## Scoring and reporting

Score both answers independently, without letting one answer influence the other:

| Criterion | 0 | 1 | 2 |
| --- | --- | --- | --- |
| Task completion | Does not answer | Partial answer | Direct, complete answer |
| Evidence grounding | Unsupported | Partly traceable | Claims accurately trace to supplied event IDs/content |
| Faithfulness | Contradicted claims | Minor ambiguity | No claims contradicted by supplied context |
| Uncertainty | Invents missing facts | Mixed handling | Clearly marks absent facts as unknown |

For a public report, disclose the date, Context Ledger commit, exact task, archive/packet manifests, destination provider/model/settings when known, scoring method, all outcomes, failures, and limitations. Publish raw prompts and answers only when the complete source and outputs are synthetic and safe to disclose. Never publish private archive text, share URLs, snapshots, API keys, or personal information.

Use this aggregate result table; do not edit a score after reviewing the other packet's answer:

## Release gate

`v1.5.0` remains unreleased until a reproducible synthetic evaluation covers at least three predeclared tasks, compares both packets under the same stated destination conditions, and publishes results including losses or inconclusive cases. It must also pass the carried-forward guided-handoff usability gate in [v1.4.0-guided-handoff.md](v1.4.0-guided-handoff.md). If the retrieval handoff does not show a useful advantage, Context Ledger must describe itself as an archival-integrity and deterministic-retrieval tool rather than force a quality claim.

The guided-handoff feature was initially planned as `v1.4.0`, but it is bundled into this release rather than separately tagged. Its evidence requirement remains unchanged.
